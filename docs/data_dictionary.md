# Data Dictionary — Workforce Retention Analytics

## Conventions

- All records are synthetic. Never import real employee personal data.
- Dates use ISO `YYYY-MM-DD`; timestamps should use ISO 8601.
- IDs are deterministic, immutable strings generated by the application. Examples include `EMP-000001`, `SURV-2026-000001`, `INT-2026-000001`, and `OUT-EMP-000001-2026`.
- SQLite uses `TEXT` for IDs, ISO dates and JSON-encoded explanation arrays; `INTEGER` for counts/flags; and `REAL` for measured numeric values.
- `NULL` means unknown, missing, not applicable, or not yet observed according to the field's definition. It must not be silently converted to a negative engagement value.
- “Available at scoring time” means the value was known by the scoring date `T`. Outcome and post-intervention fields are not allowed as features for that scoring run.
- Cross-row temporal rules (such as non-overlapping effective dates) are enforced by the Python validation layer in addition to SQL constraints.

## Relationship summary

- `Employee` 1 → many `TenureSnapshot`, `EngagementSurvey`, `WorkloadSnapshot`, `PromotionHistory`, `AttritionOutcome`, and `Intervention` records.
- `Role` and `Team` each 1 → many `EmployeeAssignmentHistory` records; the history table permits employees to move between roles and teams over time.
- `CompensationBand` 1 → many `EmployeeCompensationHistory` records.
- `RulesetVersion` 1 → many `ScoringRun` records.
- `ScoringRun` 1 → many `RetentionRecommendation` records; each employee has at most one recommendation per scoring run.
- `RetentionRecommendation` 1 → many `RecommendationReview` events and 0 → many `Intervention` records.
- `Intervention` 1 → many `InterventionEvent` records.
- `AuditLog` records traceable actions against entities by reference; `entity_id` is polymorphic and is not a foreign key.

## Validation rules beyond SQL constraints

1. Snapshot tenure must reconcile to the employee start date and snapshot date.
2. Assignment and compensation effective periods for the same employee must not overlap unless a documented exception allows it.
3. The employee must exist before any dependent record is generated.
4. Survey `Completed` requires a non-null score; missing/partial responses must not be converted into low scores.
5. Workload features must use completed periods and values available by scoring date.
6. `RetentionRecommendation.evidence_end_date` must not exceed the associated `ScoringRun.scoring_date`.
7. Attrition outcome windows and labels must reconcile with termination dates, termination type, horizon and censoring status.
8. A completed intervention requires a completion date; a cancelled intervention requires a cancellation date.
9. Intervention state changes must be permitted transitions and must have corresponding event records.
10. Ground-truth anomaly fixtures must be stored separately and must never be included in scoring/training feature tables.
11. The JSON fields in recommendations must parse and include explanations, warnings and conversation topics in the required structure.
12. Deterministic ID format, foreign-key integrity, expected row counts and reproducibility must be tested by Python.

## Important implementation note

SQLite `CHECK` constraints validate individual rows but do not fully enforce cross-table temporal logic, allowed state transitions, or non-overlapping effective date ranges. Those checks will be implemented and tested in the Python validation module in Phase 4. The schema is a starting implementation and should be verified with the project's tests before claiming full acceptance.
